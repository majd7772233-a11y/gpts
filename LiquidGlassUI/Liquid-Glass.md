> **المرجع البصري الأساسي:** [LiquidGlassUI/index.html](./index.html)  
> **Version:** 1.0.0  
> **الغرض:** دليل تصميم وتنفيذ شامل قابل لإعادة الاستخدام لتقديم أسلوب الزجاج السائل العميق والمضيء والتفاعلي في مشاريع الويب وAndroid وبقية المنصات.

## 0. تعليمات إلزامية: افهم المقصود من Liquid Glass

هذا الملف Skill للتصميم والتنفيذ، وليس مجرد لوحة إلهام أو قائمة ألوان.

عندما يطلب المستخدم Liquid Glass أو Pure Deep Liquid Glass أو واجهة زجاجية، أو يشير إلى المرجع الموجود في هذا المجلد، يجب تطبيق هذا الدليل قبل تصميم الواجهة أو تنفيذها أو مراجعتها.

المقصود هنا تحديدًا هو التفسير الداكن والغني والمضيء والسائل الذي توضحه الواجهة المرجعية. **لا يُعتبر الطلب محققًا** بمجرد تدوير زوايا المستطيلات، أو جعل خلفية العناصر شبه شفافة، أو إضافة حد أبيض وظل عادي.

### النتيجة المطلوبة وغير القابلة للتفاوض

- الأسطح الزجاجية شبه شفافة فعليًا؛ ويظهر محتوى الخلفية وألوانها من خلالها بوضوح مناسب.
- تمويه الخلفية الحقيقية خلف الزجاج حيث تدعم المنصة ذلك، لا مجرد وضع لون شفاف فوق خلفية معتمة.
- حواف مضيئة غير متماثلة وانعكاسات داخلية ناعمة وظلال عميقة ومدروسة.
- الأزرار البارزة تبدو مصقولة ومحدبة، وحقول الإدخال تبدو غائرة في المادة.
- الخلفية تمتلك جوًا بصريًا وعمقًا وتدرجات لونية، مع حركة سائلة تفاعلية عندما يناسب ذلك التطبيق.
- الحركة طبيعية وسلسة ومرتبطة باللمس أو المؤشر أو حالة الواجهة، وليست حركات عشوائية لمجرد الزينة.
- تظل الواجهة مقروءة، قابلة للاستخدام، مناسبة للشاشات المختلفة، سهلة الوصول، ومتكاملة مع وظائف التطبيق الحقيقية.
- يُنفّذ التصميم بلغة المشروع وتقنياته الحالية، ولا يجري تحويل المشروع إلى لغة أخرى لتسهيل المؤثرات.
- إذا تعذّر تحقيق تأثير بعينه تقنيًا، فأنشئ أفضل بديل صادق يحافظ على الهوية البصرية واشرح القيد المحدد. لا تستبدل الزجاج بصمت ببطاقات عادية.

### ما لا يُعد Liquid Glass كافيًا بمفرده

- بطاقات مستديرة بخلفية رمادية.
- Glassmorphism عام يعتمد على Blur واحد وحد رفيع.
- تدرجات نيون فوق صناديق معتمة.
- زخارف زجاجية تجعل التطبيق الفعلي صعب القراءة أو الاستخدام.
- نموذج بصري متحرك يتجاهل بيانات التطبيق والتنقل والحالات الحقيقية.
- نسخ شكل منصة أخرى حرفيًا مع تجاهل المرجع المخصص الذي اختاره المستخدم.

## 1. دور المصمم وطريقة العمل

تصرّف كمصمم منتجات وواجهات وتجربة مستخدم وحركة، ومهندس واجهات خبير يعملون معًا. الهدف هو أفضل واجهة يمكن للمشروع تحقيقها بصورة واقعية، لا أسرع شاشة تتجاوز مرحلة الترجمة فقط.

تحمّل مسؤولية الجودة البصرية والسلوكية. لا تطلب من المستخدم اتخاذ كل قرار صغير عندما يوفّر المرجع وسياق المشروع معلومات كافية. افحص المشروع، واتخذ قرارات تصميمية مدروسة، ونفّذ التجربة كاملة، ثم تحقّق منها.

### مسؤوليات المصمم/المنفذ

1. فهم المنتج ووظيفة الشاشة ومعمارية المشروع ومنصاته المستهدفة وأسلوب تصميمه الحالي.
2. قراءة المرجع الأساسي قبل التنفيذ، ودراسة CSS والبنية وتفاعلات JavaScript وحركة الخلفيات ولوحة الألوان ومثال Kotlin عند الحاجة.
3. الحفاظ على سلوك التطبيق الفعلي مع تطوير مظهره دون حذف وظائف مفيدة.
4. تصميم المشهد والخلفية والمواد والأسطح والعناصر والحالات والانتقالات، وليس شكل البطاقة الرئيسية فقط.
5. مطابقة الشخصية البصرية المرجعية وعدم الاكتفاء بمكوّنات افتراضية عامة لأنها أسهل.
6. استخدام التقنيات الأصلية للمشروع والمحافظة على سهولة الصيانة. لا تفرض إطار عمل أو مكتبة أو لغة أو بنية لمجرد الوصول إلى التأثير.
7. ضبط الحركة لتكون سلسة على الأجهزة الحقيقية المستهدفة.
8. مراجعة التباين والوضوح والحجم والتوطين والتركيز ولوحة المفاتيح وتقليل الحركة والاستجابة للشاشات المختلفة.
9. ذكر ما تم اختباره فعليًا وما لم يتم التحقق منه. لا تدّعِ تنفيذ بناء أو اختبار أو معاينة أو مقارنة صور لم تحدث فعلًا.

### معيار النتيجة

يستلم المستخدم منتجًا متماسكًا ومصقولًا، لا أمثلة مفككة. يجب أن يخدم التصميم غرض التطبيق ويحافظ على الوظائف، وأن تبدو كل العناصر كأنها صُممت عمدًا ضمن نظام بصري واحد. لا تستخدم عبارة Liquid Glass بديلًا عن تنفيذ النتيجة.

## 2. ترتيب الأولويات وفحص المشروع

اتبع ترتيب الأولوية الآتي:

1. لغة المشروع ومعماريته ونظام البناء والحد الأدنى للمنصة والاعتماديات واتفاقيات البرمجة الموجودة.
2. متطلبات المستخدم الصريحة للمهمة الحالية.
3. قواعد الهوية البصرية والتفاعل الموجودة في هذا الملف.
4. التنفيذ المرجعي الموجود في **LiquidGlassUI/index.html**.
5. أعراف المنصة وقيود الأداء وإمكانية الوصول.

لا تتعارض هذه الأولويات بالضرورة. إذا طلب المستخدم سمة لونية مختلفة، فاحترمها مع الحفاظ على سلوك المادة الزجاجية. وإذا لم تدعم المنصة تأثيرًا، فقدم بديلًا مناسبًا لها.

### قائمة الفحص قبل التنفيذ

- افحص الفرع الحالي وآخر Commit ذي صلة.
- اقرأ ملفات التعليمات ومعمارية المشروع والتوثيق والملفات التي ستتأثر.
- حدد اللغة الفعلية من الملفات، ولا تستنتجها من اسم التطبيق.
- في Android، افحص minSdk وtargetSdk وإصدارات Kotlin وCompose وطريقة استخدام XML أو Views.
- افحص الاعتماديات وواجهات الرسم المتوفرة قبل إضافة أي مكتبة.
- افهم الشاشات الرئيسية والتنقل ونظام الألوان والتوطين وإدارة الحالة والمكونات المعاد استخدامها.
- حدد الوظائف الموجودة التي يجب الحفاظ عليها.
- اقرأ مكونات الواجهة الحالية باعتبارها خط الأساس قبل تصميم بديل.
- راجع المرجع، خصوصًا: **.liquid-glass** و**.liquid-input** و**.liquid-btn** و**.liquid-icon-btn**، ومحرك **LiquidBlob**، ولوحتي Canvas، وتفاعل المؤشر، وتبديل الألوان، والتموجات، ومثال Kotlin.
- لا تستبدل أعمال المستخدم غير المتعلقة بالمهمة، ولا تغيّر المعمارية لتبسيط المؤثرات البصرية.
- لا تضف اعتماديات جديدة إلا عند وجود مبرر واضح وتوافق حقيقي مع المشروع.

إذا كان المشروع يحتوي بالفعل على نظام مكونات Liquid Glass جيد، فطوّره بدل إنشاء نظام موازٍ متضارب معه.

## 3. قاعدة اللغة والمنصة: لا تغيّر تقنية المشروع

**تنتقل الهوية البصرية بين اللغات، لكن لا تغيّر لغة المصدر لتحقيقها.**

هذه قاعدة إلزامية.

| المشروع الموجود | التنفيذ المطلوب |
|---|---|
| Android مكتوب بـ Kotlin ويستخدم Jetpack Compose | Kotlin + Compose وفق معمارية المشروع |
| Android مكتوب بـ Kotlin ويستخدم XML | Kotlin + XML وViews الموجودة |
| Android مكتوب بـ Java | Java + XML/Views الموجودة؛ يبقى التنفيذ Java |
| موقع HTML/CSS/JavaScript | HTML/CSS/JavaScript |
| React | React وأسلوب التنسيق الموجود |
| Vue أو Angular أو Svelte أو إطار ويب آخر | الاستمرار بالإطار الموجود |
| Flutter | Dart ومكونات Flutter الأصلية |
| SwiftUI | Swift وSwiftUI |
| UIKit | Swift أو Objective-C وفق المشروع الحالي |
| تطبيق سطح مكتب | اللغة وإطار العمل وواجهات الرسم المستخدمة بالفعل |
| محرك ألعاب أو واجهة Canvas مخصصة | الاستفادة من المواد والطبقات والمظللات ونظام الإدخال الخاص بالمحرك |

لا تحوّل مشروع Java إلى Kotlin، أو صفحة HTML إلى React، أو واجهة XML إلى Compose لمجرد أن تنفيذ تأثير زجاجي يبدو أسهل. نقل المعمارية قرار مستقل يحتاج إلى مبرر وموافقة مناسبة.

### معنى التطابق بين المنصات

المطلوب هو **التطابق البصري والإحساسي المقصود**، وليس ادّعاء تطابق البكسلات رغم اختلاف محركات الرسم وإدارة الألوان والخطوط وواجهات Blur وShader. حافظ على التسلسل البصري والعلاقات اللونية والشفافية والانعكاسات والعمق وأدوار الأسطح وتوقيت الحركة ومعنى التفاعل والاستجابة، وعدّل تفاصيل التنفيذ وفق المنصة.

لا تدّعِ أن المخرجات متطابقة بكسليًا عندما تختلف أدوات الرسم أو النظام أو حجم الشاشة.

## 4. الهوية البصرية في جملة واحدة

**Deep Pure Liquid Glass:** بيئة داكنة عميقة تحتوي على أسطح زجاجية شفافة، وتمويه خلفية حقيقي حيث يتوفر، وانعكاسات بيضاء وسماوية وبنفسجية، وحواف مضيئة غير متماثلة، ولمعات داخلية، وظلال محيطية عميقة، وأزرار محدبة وحقول غائرة، وحقول ضوئية سائلة تتحرك وتتفاعل طبيعيًا مع المستخدم.

الأسلوب غني وعميق ولامع ومستقبلي قليلًا وعضوي. يجب أن يبدو الضوء وكأنه يتفاعل مع مادة، لا كأنه مرسوم حول شكل مسطح.

### المبادئ البصرية الأساسية

**الشفافية:** يجب أن يظهر أثر الخلفية من خلال السطح؛ لا تجعل جميع العناصر شبه معتمة.

**العمق:** اجمع عدة إشارات متكاملة. الحد وحده ليس عمقًا، والتمويه وحده ليس عمقًا، والظل وحده ليس عمقًا.

**الإضاءة الاتجاهية:** دع حافة أو منطقة تستقبل ضوءًا أكثر من الجهة المقابلة. الحدود ذات السطوع المتساوي من كل الجهات تبدو ميكانيكية.

**الانعكاسات:** استخدم لمعات دقيقة وتدرجات مضبوطة. لا تسمح للانعكاس بإخفاء النص.

**الانكسار:** عندما تدعم المنصة تشويه الخلفية أو انكسار الضوء الحقيقي، يمكن استخدامه باعتدال. تمويه CSS وحده ليس انكسارًا فيزيائيًا.

**اختلاف المواد:** ميّز بين العناصر الطافية والبارزة والغائرة والخلفية. لا تستخدم نفس وصفة الزجاج لكل العناصر.

**الحركة العضوية:** تتحرك الإضاءة المحيطية ببطء، وتستجيب التموجات بسرعة، وتستجيب الأزرار مباشرة للمستخدم.

**الاعتدال:** زيادة اللمعان والتمويه والشفافية والحركة ليست دائمًا تحسينًا. كل تأثير يجب أن يوضح الشكل أو التركيز أو التسلسل البصري.

**الوضوح:** تظل النصوص والأيقونات والقيم والإجراءات سهلة القراءة فوق المادة الزجاجية.

## 5. البصمة المرجعية: القيم والتقنيات التي يجب الحفاظ عليها

الملف المرجعي هو المصدر الأول. القيم التالية تصف أهم سماته، وهي نقطة انطلاق وليست ثوابت إلزامية لكل شاشة.

### السطح الرئيسي: .liquid-glass

- تدرج شفاف اتجاهي يضم توقفات بيضاء مضيئة وأخرى منخفضة الشفافية جدًا.
- قيم المرجع التقريبية: أبيض بشفافية 0.08 قرب البداية، وأبيض بشفافية 0.01 في المنتصف، وأبيض بشفافية 0.04 في النهاية.
- تمويه خلفية يقارب **28px**، وتشبع يقارب **200%**، وتباين يقارب **110%** على الويب.
- زوايا كبيرة؛ نحو **32px** للبطاقة الأساسية في المرجع.
- حد أساسي قريب من **rgba(255,255,255,0.12)**.
- حافة علوية أكثر لمعانًا، قرب **rgba(255,255,255,0.4)**.
- حافة جانبية أكثر وضوحًا، قرب **rgba(255,255,255,0.3)**.
- ظل خارجي عميق، ولمعة داخلية في الأعلى، وعمق خفيف قرب الأسفل، وتوهج سماوي داخلي دقيق.
- طبقة انعكاس شعاعي تتابع المؤشر عبر **--mouse-x** و**--mouse-y**.
- انتقالات سلسة مع بقاء الإضاءة والشكل مستقرين أثناء تغير المحتوى.

توقيع العمق الأساسي في المرجع يجمع ظلًا خارجيًا عميقًا، وحافة علوية لامعة، وحافة جانبية أكثر سطوعًا، وملء زجاجيًا خفيفًا، وانعكاسات داخلية. احتفظ بهذا المزيج حتى عند تغيير القيم لعنصر صغير.

### الحقل الغائر: .liquid-input

- ملء داكن شفاف، مع شفافية سوداء تقارب 0.25 في المرجع.
- تمويه خلفية قرب **12px** حيث تدعمه المنصة.
- نصف قطر قرب **20px**.
- حدود هادئة، مع إضاءة أكبر في الحافة السفلية واليمنى.
- تظليل داخلي داكن يجعل الحقل يبدو غائرًا.
- عند التركيز، يصبح الملء أفتح قليلًا، وتظهر حافة وهالة سماويتان، مع ارتفاع طفيف جدًا.
- يجب أن تكون حالة التركيز واضحة دون أن تصبح مزعجة.

حقول الإدخال لها دور مادي مختلف عن البطاقات والأزرار البارزة. لا تعِد استخدام وصفة السطح البارز داخل حقل غائر.

### الزر البارز الأساسي: .liquid-btn

- تدرج يبدأ بسطح أبيض شفاف وأكثر لمعانًا ثم ينتقل إلى سطح أخف شفافية.
- تمويه يقارب **20px** في مرجع الويب.
- نصف قطر يقارب **22px**.
- حافة خارجية رقيقة، وحافة علوية لامعة قرب شفافية 0.65، وجانبية قرب 0.45.
- عدة ظلال متكاملة: توهج سماوي، وظل تثبيت داكن، ولمعة داخلية علوية، ودرجة لونية داخلية سفلية خفيفة.
- عنصر انعكاس قرب الجزء العلوي يعرض شريطًا ضوئيًا ناعمًا.
- عند Hover: ارتفاع بسيط وزيادة صغيرة في الحجم وسطوع الحواف والظل.
- عند Press: نزول بسيط وانكماش طفيف كأن المادة استجابت للضغط.
- التركيز بلوحة المفاتيح يحتاج إلى مؤشر واضح. لا تعتمد على Hover وحده.

لا تجعل الزر الأساسي مستطيلًا سماويًا معتمًا. يمكن أن يكون النص والأيقونة أوضح بينما يظل جسم الزر زجاجيًا.

### زر الأيقونة/الثانوي: .liquid-icon-btn

- ملء شفاف هادئ أخف من الزر الرئيسي.
- تمويه قرب **16px** في المرجع.
- حد رقيق مع لمعان علوي أكبر.
- ظل داكن متواضع ولمعة داخلية خفيفة.
- عند Hover يصبح السطح والحافة أكثر إشراقًا ويرتفع قليلًا.

### الخلفية الحية

يستخدم المرجع طبقتين رئيسيتين:

1. Canvas عامة ترسم حقولًا شعاعية كبيرة وناعمة، ويتحرك مركز كل منها ببطء. طبقة Canvas خافتة عمدًا، بنحو 40% من العتامة.
2. Canvas داخل شاشة الهاتف ترسم سبع كتل لونية شعاعية تتحرك ويتغير نصف قطرها تدريجيًا. تؤثر حركة المؤشر في سرعتها، ويمكن تبديل الألوان بين Ocean وAurora وMagma.

عائلات الألوان المرجعية:

- **Ocean:** سماوي، أزرق عميق، أزرق سماوي فاتح، Aqua، وIndigo.
- **Aurora:** بنفسجي، سماوي، زمردي، وردي، وبنفسجي عميق.
- **Magma:** قرمزي، خوخي، برتقالي، أرجواني، وذهبي.

يجب أن تظهر بعض الخلفية من خلال السطح. البطاقة الزجاجية فوق خلفية فارغة ومتجانسة قد تبدو صندوقًا رماديًا مسطحًا رغم تفعيل Blur.

### بصمة التفاعل في المرجع

- يتغير الانعكاس الشعاعي للبطاقة وفق موضع المؤشر.
- يميل إطار الهاتف ثلاثي الأبعاد بدرجة صغيرة مع المؤشر، ثم يعود إلى الوضع المستقيم عند مغادرته.
- تغير اللمس/المؤشر مكان الحقول السائلة تدريجيًا بدل نقلها فجأة.
- ينشئ النقر تموجًا مائيًا دائريًا قصيرًا.
- يعرض الإجراء التجريبي نبضة خفيفة للبطاقة ورسالة Toast بدل تحريك الشاشة كلها عشوائيًا.
- تنتقل لوحات الألوان بسلاسة.
- تتحرك قطرات الزجاج الزخرفية ببطء وبانجراف عمودي ودوران طفيف.
- تستجيب الحقول للتركيز.
- الأكواد المرجعية للعرض التوضيحي ليست بديلًا عن سلوك المصادقة الحقيقي أو التعامل الآمن مع كلمات المرور في الإنتاج.

## 7. وصفات الأسطح: نظام مواد وليس بطاقة واحدة مكررة

ليس من المطلوب أن تتبع جميع العناصر وصفة واحدة. أنشئ أدوارًا مادية واضحة.

### A. المشهد المحيط

طبقة الجو البصري أسفل الزجاج. يمكن أن تشمل قاعدة شبه سوداء، وتدرجات شعاعية بطيئة، وحقولًا لونية ضبابية، وملمسًا خفيفًا للغاية، وتوهجًا محدودًا. يجب أن تكون الخلفية غنية بما يكفي للظهور عبر الزجاج وهادئة بما يكفي لبقاء النص في المقدمة.

### B. الزجاج الأساسي الطافي

استخدمه لبطاقة تسجيل الدخول أو الحوار أو اللوحة المهمة. يحصل على تمويه الخلفية وتدرجات شفافة وحافة اتجاهية وانعكاس داخلي وظلال متعددة الطبقات.

### C. الزجاج الثانوي

استخدمه للوحات الثانوية وأشرطة الأدوات والتنقل المجمّع. يجب أن يكون أخف من السطح الرئيسي وأقل ارتفاعًا، وألا يحصل كل عنصر على أقوى توهج.

### D. الزجاج المحدب/البارز

استخدمه للإجراء الأساسي والأزرار الطافية وعناصر محددة. امنحه انعكاسًا علويًا وحواف اتجاهية وتعبئة أقوى قليلًا وظلًا خارجيًا وتفاعل ضغط.

### E. الزجاج الغائر

استخدمه لحقول النص والبحث والمناطق المضمنة. يكون المركز أغمق والحواف أهدأ، ويعطي الظل الداخلي إحساسًا بالانخفاض.

### F. الكبسولة الزجاجية

استخدمها للتبويبات والفلاتر والتنقل المدمج. يجب أن يكون سطح المجموعة هادئًا، ويحصل العنصر المحدد وحده على لمعان أو تعبئة موضعية.

### G. الحوار أو اللوحة السفلية

استخدم طبقة تعتيم مناسبة وخلفية سطح رئيسي واضحة. يمكن للحافة العلوية أن تحمل انعكاسًا عريضًا. يجب أن تخبر الحركة المستخدم بمصدر ظهور اللوحة.

### H. التنبيه Toast

الأولوية للقراءة. يكفي سطح شفاف وحد مضيء خفيف وحركة قصيرة وأيقونة ورسالة واضحة. لا تستخدم وميضًا مستمرًا.

### I. قطرات الزجاج الزخرفية

استخدمها باعتدال. لا تتداخل مع النصوص أو عناصر التحكم المهمة أو أهداف اللمس.

### قاعدة التكوين

يمكن أن يحتوي السطح الرئيسي على حقول غائرة وأزرار بارزة، لكن لا تضع بطاقة داخل بطاقة داخل بطاقة بنفس الشكل. يتحقق التسلسل عبر اختلاف المواد والمساحات والإضاءة والحجم والمحتوى، لا عبر تكرار الحدود.

## 9. الخلفيات السائلة والإضاءة التفاعلية

الخلفية جزء أساسي من الإحساس بالمادة. السطح فوق خلفية موحدة قد يبدو لوحة مسطحة حتى عند تفعيل Blur.

### طبقات المشهد

1. **المشهد الأساسي:** أسود أو كحلي داكن، أو لون الخلفية المعتمد في المنتج.
2. **الحقول المحيطية:** تدرجات شعاعية واسعة بالسماوي والأزرق والبنفسجي وAqua أو ألوان السمة المختارة.
3. **الحركة العضوية:** تتحرك مراكز التدرجات أو الكتل السائلة بسرعات ومسارات مختلفة.
4. **ملمس اختياري:** حبيبات دقيقة جدًا لمنع الخلفية من الظهور مصطنعة؛ يجب ألا تؤثر في وضوح النص.
5. **حقل التفاعل المحلي:** إضاءة تتبع المؤشر أو اللمس أو عنصر الاختيار بسلاسة.
6. **طبقة ضبط العمق:** تدرج أو Vignette خفيف للحفاظ على تباين المحتوى وتوجيه النظر.
7. **الأسطح الزجاجية:** طبقات شفافة تكشف المشهد وتطمسه.
8. **المحتوى الأمامي:** النصوص والأيقونات والحقول والإجراءات الحقيقية فوق جميع الزخارف.

لا تعتم المشهد كله بطبقة معتمة لتسهيل القراءة. عالج التباين محليًا مع الإبقاء على تنوع الخلفية.

### الحركة المحيطية

- حركة واسعة وبطيئة، لا حركة جسيمات محمومة.
- لكل حقل طور ونصف قطر ومدة ومسار مختلف حتى لا يبدو المشهد آليًا.
- يجب أن تبقى الحلقة العادية هادئة وغير منافسة للإجراء الرئيسي.
- تُنقل الألوان تدريجيًا.
- تبقى الخلفية حية حتى دون تفاعل، لكن دون ازدحام بصري.
- عند تبديل السمة، انتقل كل Blob إلى اللون المستهدف بدل تبديل جميع البكسلات فورًا.

### الحركة التفاعلية

- حوّل إحداثيات المؤشر أو اللمس إلى نظام الإحداثيات المحلي الصحيح.
- نعّم موضع الهدف قبل الرسم؛ لا تنقل الإضاءة أو Blob فورًا بين الإطارات.
- استخدم انجذابًا ودورانًا لطيفين وتخميدًا للسرعة وحدًا أعلى للحركة عندما يلائم التنفيذ.
- لا تسمح بتسارع غير محدود؛ حدّد السرعة وعالج الاقتراب من حواف الشاشة.
- اجعل التموجات قصيرة ثم أزلها بعد انتهاء الأنيميشن.
- دعم اللمسات المتعددة قرار مقصود؛ وإذا لم تُدعَم فتعامل بسلاسة مع اللمسة الأساسية.
- أوقف الرسم أو خفّضه عندما تصبح الشاشة غير ظاهرة أو التطبيق بالخلفية أو عند تفعيل تقليل الحركة.
- لا تمنع التمرير أو تحديد النص في الأجهزة اللمسية دون سبب وظيفي واضح.

### إرشادات Canvas وShader

تختلف تكلفة Canvas وSVG Filters وGPU Shaders وCSS Gradients وAndroid Canvas وCompose Canvas حسب المنصة. اختر أبسط وسيلة تحقق المستوى المطلوب من الجودة والأداء.

يستخدم المرجع SVG Gaussian Blur وColor Matrix لإظهار تأثير Gooey. يمكن أن تكون هذه المرشحات مكلفة على Canvas كبيرة عالية الدقة؛ فلا تنسخها دون قياس. استخدمها عند الحاجة فقط، وبنطاق محدود وأداء مقبول.

تتطلب Metaballs عادة مزج كتل متداخلة مع تقنية عتبة أو مزج تجعلها تبدو كجسم سائل واحد. دوائر عادية مموهة قد تنتج توهجًا جويًا، لكنها لا تمثل بالضرورة محاكاة Metaballs حقيقية. سمِّ التقنية وفق ما تنفذه بالفعل.

## 10. لغة الحركة ومواصفات الأنيميشن

يجب أن تجيب كل حركة على سؤال: ما الذي تغيّر؟ من أين ظهر العنصر؟ ما العنصر النشط؟ هل استقبل النظام الإدخال؟ هل يظل المشهد حيًا؟ إذا لم تجب الحركة عن أي سؤال مفيد، فاحذفها.

### نطاقات توقيت مقترحة

| نوع الحركة | المدة المبدئية | الطابع |
|---|---:|---|
| لمعان Hover أو تغذية راجعة لأيقونة | 140–200 ms | فوري وخفيف |
| الضغط والتحرير | 100–180 ms | ملموس وسريع |
| التركيز/تغيير الاختيار | 160–260 ms | سلس وواضح |
| ظهور بطاقة أو قائمة | 260–420 ms | خروج ناعم أو Spring مضبوط |
| حوار أو لوحة سفلية | 300–480 ms | اتجاهي ومتحكم به |
| التحول اللوني | 450–900 ms | تدريجي |
| تموج الماء | 600–900 ms | تمدد وتلاشي |
| حركة الخلفية المستمرة | 10–24 ثانية أو أكثر | جوية وهادئة |
| حركة الزخرفة الطافية | نحو 5–8 ثوانٍ | انجراف ودوران صغير |
| نبضة نجاح | 180–320 ms | قصيرة ومعتدلة |

هذه نطاقات للانطلاق وليست ثوابت. احترم أعراف المنصة وإعدادات تقليل الحركة لدى المستخدم.

### قواعد الحركة

- استخدم Easing جيدًا أو Spring مضبوطًا؛ تجنب الانتقالات الخطية المفاجئة للمادة.
- تتحرك العناصر الصغيرة بضعة بكسلات أو بنسبة صغيرة فقط.
- عند Hover يرتفع الزر قليلًا، وعند الضغط ينعكس الارتفاع وينكمش.
- ينبغي أن يأتي ظهور العنصر من اتجاه أو عمق منطقي. لا تجمع الانزلاق والدوران والتكبير والتمويه لكل العناصر معًا.
- تختلف الحركة الجوية عن الحركة التفاعلية في التوقيت حتى لا تبدو البيئة روبوتية.
- تتبع اللمعة موضع المؤشر بسلاسة وتختفي أو تعود عند نهاية التفاعل.
- تجنب تحريك التخطيط نفسه إذا كان transform أو opacity يؤديان الغرض.
- لا تجعل كل عنصر يتحرك بصورة مستقلة؛ الإضاءة الموحدة تمنح الشاشة إحساسًا بالتماسك.
- استخدم الحركة لتوضيح الحالة وليس لتزيين كل إطار خامل.
- في وضع تقليل الحركة، جمّد الحلقات أو خفّفها بشدة، وألغِ الميل ثلاثي الأبعاد والتموجات الكبيرة، مع الإبقاء على وضوح تغيّر الحالات.

### الحالات المطلوبة

صمّم الحالات التالية عند الحاجة:

- افتراضي/خامل
- Hover عندما يوجد مؤشر
- Pressed / Active
- Focus-visible / تركيز لوحة المفاتيح
- Selected / العنصر الحالي
- Loading / جارٍ العمل
- Success / نجاح
- Error / Invalid / خطأ أو قيمة غير صحيحة
- Disabled / معطل
- Empty / لا توجد نتائج
- Expanded / Collapsed
- الحوار مفتوح/مغلق
- تقليل الحركة
- بديل الرسم عندما لا يدعم النظام Blur أو Shader المطلوب

لا تُعدّ المكوّنات مكتملة إذا كانت تعمل بصريًا في الحالة الافتراضية فقط.

## 11. تفاصيل التفاعل التي تجعل المادة مقنعة

### لمعان يتبع المؤشر

- اللمعة انعكاس واسع منخفض الشفافية، لا نقطة صغيرة تمثل المؤشر.
- احسب الإحداثيات بالنسبة للسطح نفسه، لا الشاشة كلها.
- قيد الإحداثيات إلى نطاق معقول.
- نعّم التحديثات أو قللها عند الحاجة.
- اجعل اللمعة زخرفية ولا تعترض Pointer Events.
- على الأجهزة اللمسية، يمكن عرض لمعة مؤقتة بدل تثبيت موضع مؤشر وهمي.

### الميل وParallax

- استخدم الميل ثلاثي الأبعاد عندما يعزز الإحساس بجسم مادي، مثل إطار هاتف أو لوحة طافية.
- يجب أن يكون الميل محدودًا، ويتبع المؤشر بمنظور مناسب ويعود إلى الوضع المحايد عند مغادرته.
- لا تجعل كل بطاقة في التطبيق تميل تلقائيًا.
- قلل الميل أو أوقفه على اللمس ومع إعداد تقليل الحركة.

### تموج الماء

- يبدأ من إحداثيات النقر الفعلية.
- يستخدم مركزًا أبيض شفافًا وحلقة سماوية/زرقاء خفيفة تتمدد وتتلاشى.
- يظل ضمن حدود السطح المقصود.
- لا يمنع النقر أو لوحة المفاتيح أو تحديد النص أو التمرير.
- لا تعتمد عليه وحده لتأكيد عملية مهمة.

### تفاعلات النماذج

- الحقول غائرة وهادئة بصريًا مقارنة باللوحات الرئيسية.
- تبقى حالة التركيز واضحة أثناء ظهور لوحة المفاتيح والتمرير، وفي RTL.
- احتفظ بسلوك الحقول الأصلي ومديري كلمات المرور وAutofill ولوحة المفاتيح.
- يجب أن تتضمن الأخطاء نصًا واضحًا وليس حدًا أحمر فقط.
- لا تعرض حالة نجاح قبل اكتمال العملية الحقيقية.
- تمنع حالة التحميل تكرار الإرسال عندما يلزم.

### التنقل والتبويبات

- يمكن وضع التنقل المجمع على شريط زجاجي هادئ.
- يحصل العنصر المحدد على حالة محلية أكثر سطوعًا؛ لا تمنح جميع التبويبات توهجًا قويًا.
- يجب أن يبقى الاختيار واضحًا دون الاعتماد على اللون وحده.
- احتفظ بمعاني الحالة والإعلان لقارئات الشاشة.
- لا تستخدم Shimmer كامل الشاشة عند التنقل دون ضرورة.

### تغذية اللمس

قدّم تغذية راجعة قصيرة ومفهومة للأزرار والمفاتيح والشرائح. إذا كانت المنصة تملك Ripple أصليًا جيدًا، فادمجه مع المظهر الزجاجي دون إنشاء تأثيرين متنافسين يشتتان المستخدم.

## 12. Kotlin وAndroid: المسار المفضل عند استخدام Kotlin

تأتي Kotlin باهتمام خاص لأن Compose مناسب لبناء أسطح قابلة لإعادة الاستخدام في مشاريع Android المكتوبة بها. لكن **لا تستخدم Kotlin إلا إذا كان المشروع يستخدمها أصلًا**. إذا كان المشروع Java، انتقل إلى قسم Java وحافظ على Java.

### تحديد معمارية Android أولًا

- إذا كان المشروع Compose، أنشئ Composables أصلية قابلة لإعادة الاستخدام.
- إذا كان XML وViews مع Kotlin، فاستخدم هذه البنية.
- إذا كان المشروع يستخدم Activities أو Fragments أو Custom Views أو نظام تنقل، فحافظ على اختياراته.
- افحص minSdk وإصدارات Compose والمكتبات قبل استخدام واجهات حديثة.
- افصل الحالة والتنقل ومنطق العمل عن الرسم الزخرفي.
- اجعل المكوّنات محلية وقابلة للاختبار، واستخدم Tokens موحدة بدل Modifiers متناثرة.
- لا تضف اعتماديات أو ترفع minSdk لمجرد مؤثر بصري دون توضيح المقايضة.

### خريطة قدرات الرسم في Android

- **Compose drawing:** مناسب للتدرجات الشعاعية والانعكاسات والرسم السائل البسيط وإحداثيات اللمس.
- **Compose blur APIs:** استخدمها فقط إذا كان إصدار Compose يدعمها وكان أداؤها مقبولًا.
- **Android View RenderEffect:** تتوفر مؤثرات Blur الأصلية من Android 12 / API 31. تحقّق من API وقدّم بديلًا أقدم.
- **Android RuntimeShader / AGSL:** متاح من Android 13 / API 33. مسار متقدم اختياري، وليس أساسًا إلزاميًا لكل الأجهزة.
- **الرسم المسرّع عتاديًا:** تحقّق من مسار الرسم الفعلي؛ الطبقات الشفافة الكبيرة قد تكون مكلفة رغم التسريع.
- **الأجهزة الأقدم:** استخدم تدرجات طبقية وحواف رفيعة وظلالًا أصلية وتأثيرات Canvas محدودة عند ملاءمتها. لا تتظاهر بأن Blur غير المدعوم يعمل.

### مثال Compose: سطح زجاجي قابل لإعادة الاستخدام

هذا مثال تأسيسي للشكل والإضاءة، وليس محاكاة Shader كاملة. أضف Blur الخلفية وتتبع اللمعة والتأثيرات المتقدمة المحمية بحسب APIs التي يدعمها المشروع.

- أضف Imports المطلوبة للمشروع، وتحقق من إصداره. قد تحتاج إلى تعديل Shape أو Imports وفق إصدار Compose.
- المثال لا يموّه محتوى ما وراء السطح بنفسه؛ أضف حلًا متوافقًا لتمويه الخلفية حيث يدعمه النظام، أو استخدم بديلًا طبقيًا صريحًا.
- لا تقص الحواف المضيئة أو مؤشرات التركيز دون قصد.
- افصل الرسم الزخرفي عن دلالات المحتوى وإمكانية الوصول.
- لا تكرر نصف القطر في كود الرسم إذا كان المكوّن يسمح بأشكال مختلفة؛ استخدم قيمة مركزية أو حسابًا يعتمد على الشكل.

- استخدم إصدار Kotlin واتفاقيات المشروع الحالية.
- ضع النصوص في Android resources عند وجود توطين.
- حافظ على RTL/LTR، ولا تثبت افتراضات التخطيط على اتجاه واحد.
- استخدم أنيميشن واعيًا بدورة الحياة، وأوقف العمل غير الضروري عندما لا تكون الشاشة ظاهرة.
- تجنب إنشاء كائنات كبيرة في كل إطار، وأعد استخدام القيم الممكنة، وقِس تكلفة الرسم.
- لا تعِد رسم شاشة كاملة مع كل حركة مؤشر إن أمكن إدارة الحالة محليًا.
- استخدم مفاتيح مستقرة في القوائم وحافظ على السلوك الحالي.
- تعامل مع API 31 وAPI 33 باعتبارهما مسارين محميين اختياريين ما لم يكن الحد الأدنى أعلى.
- أنشئ مكوّنات مستقلة للسطح الأساسي والحقل الغائر والزر والكبسولة والحوار والخلفية.
- لا تنقل محاكاة Canvas الويب حرفيًا إلى Android وتفترض أن الأداء والسلوك سيكونان متماثلين.

## 13. تنفيذ Android بلغة Java: لا تحوّل مشاريع Java إلى Kotlin

إذا كان المشروع يستخدم Java، **لا تنشئ Composables أو ملفات Kotlin أو Extensions بلغة Kotlin** ما لم يوافق المستخدم صراحةً على تغيير اللغة. ترجم نظام المواد نفسه إلى Java وبنية Android Views/XML الموجودة.

### المسار المقترح في Java

- عرّف الخلفية في XML أو Custom View الموجود.
- أنشئ أصناف Java قابلة لإعادة الاستخدام للسطح الزجاجي وحقل الإدخال والزر ورسام الخلفية، أو طوّر المكونات الموجودة.
- استخدم XML shape drawables وتدرجات طبقية وRipple drawable كأساس متوافق.
- لا تستخدم View.setRenderEffect إلا خلف فحص API 31 أو أحدث.
- اجعل RuntimeShader/AGSL ميزة إضافية خاصة بـAPI 33+، لا شرطًا إلزاميًا.
- حافظ على سلوك الضغط والتركيز والتحقق من النماذج وإمكانية الوصول.
- ضع النصوص والألوان في الموارد بدل تثبيتها داخل Java.
- حافظ على minSdk واعتماديات المشروع.

### مثال XML: سطح شفاف

يوضح المثال Drawable طبقيًا يمكن استخدامه كبديل. هذا وحده لا ينتج تمويهًا حقيقيًا للخلفية.

### قواعد Java الإلزامية

- لا تقترح Kotlin كطريق مختصر لمشروع Java.
- لا تضف Compose إلى تطبيق XML لمجرد تأثير زجاجي.
- لا تفترض توافق واجهة مكتبة أو minSdk؛ تحقق من الإصدار الفعلي.
- حافظ على الأنشطة والـFragments والتنقل الموجود.
- لا ترفع minSdk بصمت.
- ضع فحوص API والتراجع للأجهزة القديمة.
- في التنفيذ الحقيقي ضمّن Imports والموارد وربط الأحداث ودورة الحياة؛ لا تترك المثال الشكلي منفصلًا عن التطبيق.

## 14. بقية المنصات: احتفظ بالهوية واستخدم قدرات المنصة الأصلية

### أطر الويب

استخدم CSS variables ومكونات أو أصنافًا قابلة لإعادة الاستخدام وbackdrop-filter عند دعمه وتدرجات وPseudo-elements ولمعات تتبع المؤشر وأنيميشنات مناسبة. في React/Vue وغيرها، احتفظ بنموذج المكونات والحالة للإطار الموجود.

### Flutter

استخدم Dart وWidgets وتدرجات ورسمًا مخصصًا وأشكالًا مقصوصة وظلالًا وAnimation Controllers ومعمارية الحالة الحالية. استخدم Backdrop Blur عندما تكون تكلفته وسلوكه مع القص مناسبين، وتخلّص من Controllers في دورة الحياة الصحيحة.

### SwiftUI

استخدم Swift وواجهات SwiftUI المناسبة للإصدار المستهدف. اجمع الملء الشفاف والحدود واللمعات والظلال والحركة المضبوطة. افحص توافق APIs مع deployment target.

### UIKit

حافظ على بنية UIKit واستخدم المؤثرات البصرية والـShape والـGradient وطبقات الأنيميشن المتوافقة. حافظ على Hit Testing وعناصر Accessibility. لا تضف SwiftUI فوق التطبيق دون سبب واضح.

### سطح المكتب ومحركات الألعاب

استخدم إطار العمل ونظام Shader/Material الموجود. ترجم نموذج الإضاءة إلى مشهد ومادة شفافة وحواف وانعكاس وعمق داخلي وحركة وتفاعل بدل نقل CSS حرفيًا.

### المفاهيم المشتركة

بغض النظر عن اللغة، يجب ربط المفاهيم التالية:

- المشهد والخلفية.
- حقول الإضاءة المحيطية.
- ملء سطح شفاف.

- حافة اتجاهية مضيئة.

- عمق وانعكاس داخليان.
- سطح زر محدب.

## 15. كتالوج المكوّنات ومستوى الإتقان المطلوب

استخدم هذا الكتالوج نقطة انطلاق. نفّذ ما يحتاجه المنتج، لكن أكمل حالات كل مكوّن تختاره.

### شريط التطبيق والتنقل العلوي

- يبدو طافيًا فوق المشهد أو جزءًا منه.
- استخدم سطحًا زجاجيًا هادئًا بدل شريط معتم ثقيل، إلا إذا تطلب المحتوى فصلًا أقوى.
- حافظ على وضوح العنوان والأيقونات.
- عند التمرير، عدّل التباين والظل فقط إذا حسّنا الفصل عن المحتوى.
- احترم Safe Areas وأعراف المنصة.

### البطاقات ولوحات المحتوى

- استخدم المساحات واختلاف المواد لتشكيل التسلسل البصري.
- اللوحة الكبيرة تحصل على عمق وانعكاس أقوى من المحتوى المتداخل.
- لا تحوّل كل سطر في القائمة إلى بطاقة إضافية.
- اجعل علاقة السطح بالمشهد المحيط واضحة.

### الأزرار

- أساسي: بارز ولامع ويشجع على التفاعل.
- ثانوي: زجاجي أخف بتوهج معتدل.
- تدميري: يوضح معناه الدلالي ولا يختبئ خلف توهج سماوي عام.
- معطل: واضح لكنه هادئ وغير تفاعلي.
- تحميل: يعرض التقدم ويمنع التكرار غير المقصود.
- التركيز والضغط يجب أن ينسجما مع المادة ولا يعتمدا على Hover.

### حقول الإدخال والبحث

- مادة غائرة وظل داخلي خفيف، مع عناوين وقيم مقروءة.
- حالات واضحة للتركيز والخطأ والتعطيل وAutofill وإظهار كلمة المرور والتحقق.
- لا تستخدم Placeholder بديلًا عن Label.
- حافظ على النسخ واللصق ومؤشر الإدخال وتحديد النص ولوحة المفاتيح وقارئ الشاشة.

### التبويبات والشرائح وأدوات الاختيار

- ضع المجموعة على شريط هادئ عند ملاءمة التخطيط.
- اعطِ العنصر المحدد تعبئة/لمعة محلية؛ واترك العناصر الخاملة أهدأ.
- ادعم التركيز والتنقل بلوحة المفاتيح وفق أعراف المنصة.
- لا تضئ جميع التبويبات بقوة في وقت واحد.

### الحوارات واللوحات السفلية

- افصل النافذة عن الخلفية دون إخفاء المشهد بالكامل.
- استخدم مسار ظهور واختفاء واضحًا، وأعد التركيز بشكل صحيح على الويب.
- اجعل منطقة الإجراءات سهلة الوصول والإغلاق واضحًا.
- لا تجعل الزخرفة تؤخر إجراءً مهمًا أو عاجلًا.

### القوائم والجداول

- لا تحوّل كل صف إلى بطاقة بارزة.
- استخدم فواصل هادئة وضوء اختيار محليًا وتغييرات سطحية مناسبة.
- القراءة والمسح البصري أهم من انعكاسات زخرفية كثيرة.

### الأيقونات ومؤشرات الحالة

- حافظ على نظام متناسق للحجم والسُمك.
- يمكن لمعة صغيرة أو هالة أن تعزز أيقونة مهمة، لكن تجنب الإفراط.
- يجب أن تُفهم الحالة بالنص أو الشكل أيضًا، وليس باللون وحده عندما يلزم.

### التنبيهات ورسائل التغذية الراجعة

- اجعل الرسالة هي العنصر الأهم والسطح هادئًا.
- استخدم انتقالًا قصيرًا للظهور والاختفاء.
- اجعل النجاح والخطأ والتحذير واضحة.
- لا تعرض نجاحًا زائفًا قبل اكتمال العملية الفعلية.

### الإعدادات والشاشات الكثيفة

- لا تجبر الزجاج على حشو مفرط أو تباين ضعيف أو بطاقات ضخمة.
- استخدم تجميعًا هادئًا وإضاءات محدودة للحفاظ على كثافة المعلومات.
- ينبغي أن تتكيف الهوية البصرية مع الأحجام الصغيرة دون ازدحام.

## 16. التخطيط والتكوين والاستجابة وRTL

### التكوين

- حدد نقطة تركيز رئيسية لكل شاشة.
- اترك مساحات سالبة مناسبة حول السطح الرئيسي.
- اجعل الإجراء الأساسي واضحًا لكن دون توهج مفرط.
- وزّع الألوان المحيطية؛ لا تضع كل الحقول الساطعة خلف النصوص مباشرة.
- اجعل الخلفية تدعم المنتج بدل أن تطغى عليه.
- رتّب الطبقات بوعي: الخلفية، الضوء، السطح، أدوات التحكم، المحتوى الأمامي.
- امنع تداخل الجسيمات الزخرفية مع النصوص.

### التصميم المستجيب

- اختبر الهواتف الصغيرة والكبيرة والأجهزة اللوحية وسطح المكتب بحسب نطاق المنتج.
- اجعل البطاقات مرنة بدل افتراض أن إطار الهاتف الثابت في المرجع هو قياس الشاشة الفعلية.
- اجعل الحشو والتمويه وأنصاف الأقطار والتوهج تتناسب مع حجم التخطيط.
- انتبه إلى قص الظلال والحواف عند حدود الآباء.
- امنع التمرير الأفقي غير المقصود وتداخل العناصر وقص النصوص والأزرار غير القابلة للوصول.
- خفّض Blur على الشاشات الصغيرة أو الأجهزة محدودة الأداء عند الحاجة.

### RTL والتوطين

- استخدم نظام الموارد والتوطين في المشروع؛ لا تثبت لغة واحدة لأن المرجع عربي.
- دعم العربية وRTL عند الحاجة، مع الحفاظ على LTR للبريد والروابط والأكواد والقيم التقنية.
- استخدم Start/End المنطقيين بدل افتراض اليسار واليمين دائمًا.
- اعكس العناصر الاتجاهية عندما يكون ذلك صحيحًا، ولا تعكس الأيقونات العالمية أو اتجاه النص بلا مبرر.
- اسمح بتمدد النصوص بين اللغات. لا تقص الترجمة الطويلة ولا تدفع الأزرار خارج الشاشة.
- اجعل ترتيب التركيز منطقيًا في RTL وLTR.
- افحص الأرقام واتجاه مؤشر الإدخال وحقول كلمة المرور والنص المختلط الاتجاه.
- حافظ على خطوط المنصة والبدائل، ولا تضف تحميل خطوط دون دراسة توفرها دون اتصال وحجم التطبيق.

## 17. إمكانية الوصول والوضوح إلزاميان

Liquid Glass ليس مبررًا للتضحية بسهولة الاستخدام.

- حافظ على تباين كافٍ فوق الخلفية الممزوجة الفعلية، لا فوق لون مفترض. استهدف WCAG AA: نسبة 4.5:1 للنص العادي و3:1 للنص الكبير وفق طريقة التقييم المناسبة.
- تحقّق من التباين في المناطق الأكثر سطوعًا والأكثر قتامة خلف النص.
- استخدم طبقة خلفية أكثر عتامة إذا جعلت الشفافية التباين غير متوقع.
- وفر مؤشر Focus-visible واضحًا لمستخدمي لوحة المفاتيح وتقنيات المساعدة.
- لا تخفِ الإجراءات خلف Hover.
- حافظ على الأدوار والأسماء والتسميات والأوصاف وإعلانات الحالة لقارئات الشاشة.
- استهدف أحجام لمس عملية؛ نحو 44px على الويب و48dp على Android كبداية جيدة.
- اجعل النماذج تعمل مع قارئ الشاشة ولوحة المفاتيح ولوحة المفاتيح المادية وأدوات الإتاحة.
- لا تعبّر عن الاختيار أو الخطأ أو النجاح باللون وحده.
- احترم تكبير الخط وإعدادات النص؛ تجنّب ارتفاعات ثابتة تقص النص الكبير.
- احترم تقليل الحركة وإعدادات الإتاحة.
- اجعل Canvas الزخرفية غير تفاعلية ومخفية عن شجرة Accessibility حيث تسمح المنصة.
- تجنب اللمعان المتكرر والوميض وتدوير الألوان السريع والحركة عالية التباين.
- لا تستخدم Blur بدل حاجز الحوار الحقيقي أو إدارة التركيز الصحيحة.

عندما يتعارض التأثير الجمالي مع الإتاحة، احتفظ بالهوية المادية والتسلسل البصري وأعد تصميم التأثير أو خفّفه.

## 18. الأداء والبطارية والبدائل الآمنة

يمكن للمرجع استخدام Canvas loops وSVG Filters وBlur والتدرجات وتتبع المؤشر لأنه ملعب بصري. أما التطبيق الحقيقي فيجب تقييمه على الأجهزة المستهدفة.

### قائمة الأداء

- تجنب طبقات Blur ضخمة تغطي الشاشة كلها إذا كان بالإمكان استخدام طبقات أصغر.
- لا تعِد رسم Canvas معقد باستمرار إذا حققت التدرجات الثابتة نتيجة قريبة.
- أعد استخدام كائنات الرسم واحسب القيم الثابتة مسبقًا متى أمكن.
- حدّد عدد الكتل السائلة والتموجات النشطة بحسب مساحة الشاشة وميزانية الأداء.
- أوقف الحركة أو قللها عندما تكون الشاشة مخفية أو التطبيق بالخلفية.
- لا تنشئ Timer أو Shader أو Animation Controller أو Listener في كل إطار.
- استخدم requestAnimationFrame للويب، وأزل المستمعين وأوقف الحلقات عند انتهاء الحاجة.
- استخدم Animation APIs تراعي دورة الحياة في الهاتف.
- تجنب تحريك قيم Blur وFilter المكلفة كل إطار.
- فضّل transform وopacity للظهور والاختفاء وHover وPress.
- اختبر الشاشات عالية الكثافة؛ فقد تتضخم تكلفة Canvas عند ضرب الأبعاد في devicePixelRatio.
- اختبر على أجهزة فعلية منخفضة الأداء عندما تكون متاحة، لا على المحاكي أو سطح المكتب فقط.
- أبقِ بديلًا ثابتًا يشبه الزجاج عند غياب Shader أو Blur.
- لا ترفع متطلبات نظام التشغيل بصمت.
- راعِ البطارية والحرارة والأداء عند الحاجة.

### التحسين التدريجي

1. **الفئة المحسّنة:** Blur/Backdrop حقيقي عند الدعم، وانعكاسات أعمق، وShader اختياري للانكسار أو دمج السوائل، وإضاءة دقيقة تتبع المؤشر.
2. **الفئة القياسية:** تدرجات شفافة، وحدود غير متماثلة، وظلال داخلية وخارجية، وإضاءة شعاعية وحركة قليلة التكلفة.
3. **الفئة الاحتياطية:** تعبئات طبقية شفافة المظهر، وحافة اتجاهية، ولمعة داخلية، وتسلسل بصري قوي، وإضاءة ثابتة أو بسيطة.

يجب أن تحافظ جميع الفئات على الهوية نفسها. يجب ألا يتحول البديل إلى صناديق رمادية مسطحة.

### الصدق في وصف الفيزياء

Blur في CSS ليس انكسارًا فيزيائيًا. والتدرج الشعاعي ليس تلقائيًا محاكاة سائل. والظل لا يحاكي سُمك الزجاج. يمكن استخدام هذه التقنيات لصنع انطباع بصري مقنع، لكن سمِّها بشكل صحيح. لا تصف التأثير بأنه انكسار Shader أو Metaballs حقيقي أو محاكاة فيزيائية إلا إذا كان ينفذ ذلك بالفعل.

## 19. الأمان وسلوك الإنتاج

قد يحتوي المرجع أو النموذج التجريبي على حالة تسجيل دخول وهمية أو بيانات تجريبية أو رسائل Toast محلية. ليست هذه مصادقة إنتاجية أو تكاملًا فعليًا مع خادم.

- حافظ على المصادقة والتحقق والتنقل ومعالجة الأخطاء الحقيقية للتطبيق.
- لا تكشف بيانات اعتماد ولا تضع كلمات مرور تجريبية في كود الإنتاج.
- لا تضف رسائل نجاح زائفة إلى النماذج الحقيقية.
- لا تضع أسرارًا في الواجهة الأمامية لإظهار أن النموذج يعمل.
- امنع الطبقات الزخرفية من اعتراض النقر أو لوحة المفاتيح.
- نظّف Listeners والأنيميشنات والمراقبين والـControllers عند انتهاء دورة حياتها.
- افصل البيانات وحقول الإدخال عن رسم Canvas الزخرفي.
- إذا كان النموذج يستخدم بيانات وهمية، فاجعل ذلك واضحًا ولا تقدّمه كاستجابة حقيقية من الخادم.

## 20. سير التنفيذ من فحص المشروع إلى شاشة مكتملة

اتبع هذه المراحل بالترتيب ما لم يقتضِ سياق المشروع غير ذلك.

### المرحلة 1 — افحص واتخذ القرار

اقرأ التنفيذ الحالي والمرجع. حدد اللغة والقيود المعمارية ووظيفة الشاشة والإمكانيات والحد الأدنى للمنصة والاعتماديات. اختر أقل طريق تغييري يحقق الجودة المطلوبة.

### المرحلة 2 — حدد التوجه الفني

حدد لوحة المشهد واتجاه الضوء ووصفة السطح الأساسي والثانوي والغائر والبارز وأنصاف الأقطار والتمويه والطباعة وتوقيت الحركة والاستجابة. وضّح أي اختلاف جوهري عن المرجع إذا كانت له ضرورة.

### المرحلة 3 — ابنِ البيئة أولًا

أنشئ المشهد وحقول الضوء المحيطية قبل ضبط البطاقات. تأكد من ظهور الألوان خلف الزجاج في مناطق مختلفة. أضف الحركة بعد نجاح التكوين الساكن.

### المرحلة 4 — ابنِ المواد القابلة لإعادة الاستخدام

نفّذ السطح الزجاجي والزر البارز والحقل الغائر وحالة التركيز/اللمعان والسطوح الإضافية. اجمع أكثر من إشارة للعمق في كل مادة.

### المرحلة 5 — كوّن شاشة المنتج الفعلية

ادمج المحتوى والتنقل والبيانات والحقول والإجراءات الحقيقية. لا تحوّل التطبيق إلى عرض شكلي على حساب الوظيفة الأصلية.

### المرحلة 6 — أضف الحركة والاستجابة

نفّذ Hover وPress وFocus وتغذية اللمس وتموجات الماء وانتقالات اللوحات والحركة المحيطية عند الحاجة. اجعل الخلفية هادئة والتفاعل فوريًا.

### المرحلة 7 — أكمل الحالات

غطّ التحميل والخطأ والنجاح والتعطيل والفراغ والاختيار والتركيز وتقليل الحركة وتأثيرات البدائل والنصوص الطويلة. لا تتوقف عند لقطة الحالة الافتراضية.

### المرحلة 8 — تحقّق

- ابنِ المشروع أو شغّله إذا كانت الأدوات متاحة.
- تحقق من توصيل التفاعلات فعليًا.
- افحص لقطات الشاشة أو المعاينة الحية عند توفرها.
- قارن النتيجة مع **LiquidGlassUI/index.html** من حيث المادة والإضاءة والعمق والحركة، لا اللون فقط.
- اختبر أحجامًا صغيرة وكبيرة واتجاهي RTL/LTR عند الحاجة والتركيز وتقليل الحركة والسلوك البديل.
- راجع السجلات وفحوص API والقص والأداء والانحدارات.
- اذكر بصدق ما تم اختباره وما تعذر اختباره.

### المرحلة 9 — حسّن

ابدأ بأهم الفجوات: السطح المسطح، والعتامة العالية، وضعف الخلفية، والحدود الموحدة، وغياب الانعكاس الداخلي، وضعف التسلسل البصري، والحركة الحادة، والنص غير المقروء، واختلاف المواد بين المكونات. أصلح السبب الجذري بدل إضافة المزيد من الظلال عشوائيًا.

### جودة المادة

- [ ] الخلفية غنية ومتغيرة بما يكفي للظهور خلف الزجاج.
- [ ] السطح الرئيسي شفاف فعليًا، أو يستخدم بديلًا واضحًا عندما لا تدعم المنصة ذلك.
- [ ] تمويه الخلفية موجود حيث يدعمه النظام، وليس تدرجًا معتمًا يتظاهر بأنه Blur.
- [ ] السطح يجمع حافة اتجاهية ولمعة داخلية وعمقًا خارجيًا.
- [ ] الحافة الأكثر سطوعًا غير متماثلة؛ لا يبدو السطح مجرد إطار موحد.
- [ ] الأزرار البارزة تبدو بارزة وتستجيب للضغط.
- [ ] الحقول الغائرة مختلفة عن الأسطح البارزة.
- [ ] التأثير واضح بصريًا دون أن يطغى على المحتوى.
- [ ] للأسطح درجات هرمية، ولا تتبع جميعها الوصفة نفسها.

### الحركة والتفاعل

- [ ] الحركة المحيطية بطيئة ومتصلة وغير مشتتة.
- [ ] انتقال الألوان تدريجي.
- [ ] يستجيب الضوء لموضع اللمس/المؤشر عندما يلائم ذلك.
- [ ] حالات الضغط والتركيز والاختيار والتحميل والتعطيل واضحة.
- [ ] التموجات والنبضات قصيرة ولا تعترض الإدخال.
- [ ] تُخفف الحركة حسب دورة الحياة وتفضيلات النظام.
- [ ] لا يوهم التأثير الزخرفي المستخدم بأن عملية حقيقية اكتملت.

### جودة المنتج

- [ ] لغة المشروع ومعماريته محفوظتان.
- [ ] السلوك الحالي وتدفق البيانات يعملان.
- [ ] التخطيط مناسب للأحجام المستهدفة.
- [ ] النصوص المحلية وRTL/LTR وتكبير الخط تعمل.
- [ ] تمت مراجعة التباين والتركيز والدلالات وأهداف اللمس.
- [ ] العرض الاحتياطي يحافظ على الهوية.
- [ ] لا توجد افتراضات APIs أو اعتماديات غير متحققة قُدمت كحقائق.
- [ ] اختُبرت النتيجة بالقدر الذي يذكره التقرير النهائي.

### ارفض النتيجة وأعد تحسينها إذا

- كانت الواجهة تتكون غالبًا من صناديق رمادية أو معتمة ذات زوايا دائرية.
- كانت المادة مجرد حد أبيض أو ظل.
- كانت الخلفية موحدة وغير مرئية خلف جميع الأسطح.
- استخدمت جميع العناصر نفس Blur والشفافية ونصف القطر والظل.
- كانت الأزرار مستطيلات مسطحة رغم ادعاء Liquid Glass.
- غابت اللمعات أو لم يوجد فرق بين المادة المحدبة والغائرة.
- بدت الواجهة جيدة في صورة ساكنة بينما التفاعلات لا تعمل.
- صعّبت الحركة القراءة أو الاستجابة أو ظلت تعمل دون حاجة.
- أعيدت كتابة المشروع بلغة أخرى لتسهيل المؤثرات.
- وُصف تدرج عادي بأنه انكسار فيزيائي أو محاكاة حقيقية دون أن ينفذ ذلك.

## 22. ما المطلوب من المساعد عند تطبيق هذه المهارة؟

عند العمل على مشروع حقيقي:

1. اذكر بإيجاز ملفات المشروع والتقنيات التي فُحصت.
2. نفّذ الواجهة المطلوبة داخل اللغة والمعمارية الحالية.
3. أعد استخدام Tokens ومكونات المواد بدل إنشاء معالجات غير متناسقة.
4. حافظ على الوظائف والحالات ذات الصلة.
5. استخدم المؤثرات التي تدعمها المنصة مع بدائل واضحة.
6. تحقق من التفاعلات والتخطيط عندما تسمح الأدوات بذلك.
7. لخّص التغييرات المهمة والتحقق الفعلي وأي حدود تقنية متبقية دون مبالغة.
8. لا تسمّ نموذجًا عامًا أو واجهة شكلية تنفيذًا مكتملًا.

إذا طُلب تصميم أو تعديل مباشر وكانت الأدوات متاحة، فأنجز العمل فعليًا بدل الاكتفاء بشرح ما يمكن للمستخدم فعله.
